01 ¿Por qué este protocolo y este modelo?

Open Responses
Estándar abierto que replica la Responses API de OpenAI. Por qué: requisito de la plataforma del reto.
Groq - gpt-oss-120b
Se buscaba una solución rápida y gratuita dado el tiempo para preparar esta demostración. Se probó primero con un modelo local (Ollama - llama3.1), sin embargo las especificaciones de la computadora en la que se hizo este desarrollo no eran suficientes para desplegar este modelo en un servidor y tener un tiempo de respuesta aceptable. Se usó la plataforma Groq para consultar modelos en línea de manera más eficiente, aunque con límites de uso.

02 Arquitectura de tools

búsqueda local

search_knowledge_base

Se indexó el archivo en formato PDF de mi CV en ChromaDB con embeddings locales (sentence-transformers), de esta manera el agente se vuelve en un agente RAG con información adicional al contexto específico, que en este caso es mi experiencia profesional.

consulta en vivo

fetch_github_profile / fetch_gitlab_profile

Se consulta la información de cuentas de github y/o gitlab si se encuentran en el CV proporcionado, pero el agente también puede buscar las URLs de perfiles de estos sitios web o buscar por nombre de usuario y devolver información acerca de repositorios públicos.

externo

web_search (SerpAPI)

Solo se invoca si el CV/GitHub/GitLab no son suficientes para responder una pregunta acerca de la persona, realiza una búsqueda web de la persona y devuelve información de sitios web que hagan match. Solo devuelve información relevante con la experiencia profesional de esta persona.

seguridad

separación de responsabilidades

Solo agente.py y agente_server.py leen variables de entorno; knowledge_base.py y tools.py reciben todo como parámetros explícitos.

Por qué: cada módulo es testeable de forma aislada, sin depender del orden de imports para tener las keys cargadas.

03 Memoria de conversación

previous_response_id
Cada respuesta trae un id; mandarlo en el siguiente request continúa la misma conversación.
Almacenamiento
Diccionario en memoria del proceso (SESSIONS), no una base de datos externa. Para esta demostración se consideró que era suficiente este tipo de memoria.

04 Despliegue: Docker + Cloud Run

Docker

Para facilitar el despliegue del agente, se considera que usar un contenedor con los paquetes suficientes es la opción ideal. Docker es la herramienta más usada para este tipo de casos y de la que tengo mejor conocimiento.

Cloud Run

La opción gratis de Cloud Run te da 2M peticiones/mes, sin costo en reposo. Es una opción popular y con menos requisitos para su uso. En lo personal, he usado Google Cloud, por lo que ya tenía una cuenta y era una opción rápida donde podía desplegar el proyecto sin gastar.

05 Confiabilidad

Tope de iteraciones
MAX_TOOL_ITERATIONS corta el loop de tool-calling en vez de dejarlo indefinido. Se detectó en producción: el modelo a veces entra en un ciclo de búsquedas reformuladas sin converger.
Errores de la API distinguidos
RateLimitError se maneja distinto de un error genérico. Encontrado en vivo:Groq tiene un tope diario de tokens por modelo (200K TPD) que se agota probando.
Fallback entre modelos
MODEL_FALLBACK_CHAIN: si gpt-oss-120b agota su cupo diario, el agente reintenta automáticamente con gpt-oss-20b antes de rendirse. Se evaluó sumar Qwen a la cadena, pero se descartó: con este agente (razonamiento + tools) agota su presupuesto de salida pensando, sin llegar a responder. Su tope de 1000 tokens de salida por minuto en Groq es insuficiente. Validado simulando ambos escenarios (un modelo caído, los dos caídos) antes de confiar en el mecanismo.
Extracción de URLs del CV
Regex corregido para no fusionar URLs separadas por | sin espacio, y para recomponer una URL partida por un salto de línea del PDF en medio del TLD. Bug real encontrado probando con el CV real: "linkedin...|www.github" se leía como una sola URL corrupta.
